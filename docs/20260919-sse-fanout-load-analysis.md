# SSE配信の負荷特性とPostgreSQL NOTIFYでの改善余地

現行のjobStatusesサブスクリプション（[backend/graph/schema.resolvers.go](../backend/graph/schema.resolvers.go)、[backend/pgpubsub/hub.go](../backend/pgpubsub/hub.go)）が抱える負荷特性を整理し、PostgreSQL NOTIFY/LISTENを使い続ける前提でどこまで改善できるかを検討したメモ。複数プロセスへのスケーリングは必須、Redisは導入しない（[backend/pubsub](../backend/pubsub)のRedis実装は参照用に残っているのみ）という制約を前提にする。

## 総評

現状の実装は「無関係なユーザーの更新でDBクエリが増える」問題は抱えていない。実際に単調増加するのは「同一ユーザーが開いているタブの本数に比例したクエリ数」であり、これは今のNOTIFY利用方法とは独立した、fan-out層の設計の問題である。NOTIFYチャンネルをユーザー単位に分割する案は有効だが、解決するのはタブ数増加問題ではなく、プロセス間での無駄な配信を減らす別の効果であり、両者を混同すると対策を誤る。

## 1. 現状の正確な負荷特性

### 1.1 タブ数に比例して増えるのはクエリ数であって、PostgreSQLへの接続数ではない

`pgpubsub.Hub`はプロセスごとにLISTEN専用の`pgx.Conn`を1本だけ張り（[hub.go:38-58](../backend/pgpubsub/hub.go)）、以後ずっと張りっぱなしで使い回す。この接続は`pgxpool`とは別物で、クエリ発行用のコネクションプールとは完全に分離されている。

タブを何枚開いても、このLISTEN専用接続が増えることはない。増えるのは、`JobStatuses`リゾルバ（[schema.resolvers.go:41-88](../backend/graph/schema.resolvers.go)）が`Subscribe`のたびに1本ずつ立てるgoroutineの数と、そのgoroutineが個別に呼ぶ`JobStore.List`のクエリ回数である。

タブが3枚あれば、同一ユーザーの更新1回につき`SELECT ... FROM jobs WHERE user_id = $1`が3回実行される。タブの枚数だけクエリが増えるこの構造が、素朴に考えるとDoSに近い性質を持つ最大の要因である。

### 1.2 無関係なユーザーの更新ではList自体が呼ばれない

`Hub.dispatch(userID)`（[hub.go:156-167](../backend/pgpubsub/hub.go)）は`h.subs[userID]`というマップの該当キーだけをループする。ユーザーBの更新はユーザーAの購読者には一切触れないため、**同一プロセス内では**無関係なユーザー分の`JobStore.List`は発生しない。ここは既に正しく絞り込めている。

無駄が生じるのはプロセスをまたいだ場合である。現状は単一チャンネル（`job_updates`）にNOTIFYを送っているため、ユーザーBの接続を1本も持たないプロセスにもこのNOTIFYは届く。届いた側は`dispatch("userB")`を呼ぶが`h.subs["userB"]`が空なので何も起きない。この無駄はマップ参照程度の軽いコストであり、`JobStore.List`のような重い処理には波及しない。

### 1.3 開いていないチャンネルへのNOTIFYは届かない

`pg_notify(channel, payload)`はチャンネルの購読者数を一切確認せずに成功する。配信は送信時点でそのチャンネルをLISTENしているセッション全員に対して行われ、購読者がいなければ何も起きずに消える。NOTIFYのペイロードは永続化されないため、後からLISTENを始めても過去の通知を遡って受け取ることはできない。

## 2. NOTIFYチャンネルのユーザー単位分割案

`LISTEN job_updates_{userID}`のようにチャンネル名をユーザーごとに分ける案。

### 2.1 何が解決し、何が解決しないか

解決するのは、複数プロセス構成における「無関係なユーザー宛の通知がすべてのプロセスに配られる」無駄である。チャンネルを分ければ、そのユーザーの接続を実際に持つプロセスにしか配信されなくなる。

解決しないのは、1.1で述べたタブ数比例のクエリ増加である。チャンネルをいくら分けても、各プロセス内で`JobStatuses`のgoroutineが個別に`JobStore.List`を呼ぶ構造は変わらない。この2つは独立した問題であり、片方の対策だけでは両方は解決しない。

### 2.2 PostgreSQL接続への影響

1接続が複数チャンネルをLISTENすること自体はPostgreSQLの設計上想定内で、LISTEN登録数の増加が物理的な接続数の増加に直結するわけではない。増えるのは「1接続が抱えるLISTEN登録の数」であり、これはPostgreSQLの`max_connections`のような明確な天井には直撃しない。ただし、登録数の増加がNOTIFY配信時の照合コストにどう効くかは実装依存の部分があり、大規模なユーザー数を想定するなら実測しておく価値がある。

複数プロセス（バックエンドの水平スケール）で同じチャンネル名（例えば`job_updates_user1`）をLISTENした場合も問題なく機能する。NOTIFYは「1対1のキュー」ではなく「同じチャンネル名をLISTENしている全セッションへのブロードキャスト」であり、プロセスAとプロセスBが両方とも`job_updates_user1`をLISTENしていれば、`pg_notify('job_updates_user1', ...)`は両方のプロセスに届く。片方が受信すると消費されてもう片方には届かない、という排他的な取り合いにはならない。ユーザー1のタブがプロセスAとプロセスBに分散して接続していても、どちらのプロセスも通知を取りこぼさない。これはNOTIFY/LISTENが元々持つ複数プロセスへの配信性質であり、ユーザー単位のチャンネル分割を導入してもこの基本挙動は変わらない。

ただし、プロセスごとに抱えているタブ数分だけクエリが重複する問題（1.1）はプロセスごとに独立して発生する点に注意する。プロセスAが5タブ、プロセスBが3タブを抱えていれば、1回の更新で合計8回の`JobStore.List`が走る。これは3.で述べる「dispatch時に1回だけList」の改善をプロセスごとに適用することで解消する話であり、複数プロセスであること自体がこの対策の必要性を弱めるわけではない。

### 2.3 新たに背負うコスト

- **動的なLISTEN/UNLISTEN管理が必要になる。** 現状はプロセス起動時に単一チャンネルを1回LISTENするだけで済んでいたが、ユーザー単位に分けると「最初の接続でLISTEN開始、最後の接続切断でUNLISTEN」という参照カウント方式の管理が要る。
- **LISTEN発行の完了より先にGoのマップへ購読者を登録すると、その間の更新はPostgreSQLからそもそも配信されない。** `Hub.dispatch`は`triggerCh`をバッファ1のチャンネルとして使っており、Subscribe直後に届いた通知を取りこぼしても、バッファに残った通知をきっかけに次のループでListをやり直せば最終的な状態は復元される（[hub.go:160-165](../backend/pgpubsub/hub.go)のコメント参照）。したがって「Goのプロセス内に通知が届いた後の取りこぼし」は既存の設計で自己修復するため、動的LISTEN方式でも「LISTEN完了後にもう一度List」のような追加のクエリは不要であり、むしろ過剰な対策になる。真に注意すべきは、PostgreSQLへのLISTEN発行が完了する前に購読者登録だけ先に済ませてしまうと、その間の更新はGoのプロセスに一切届かず、この自己修復の射程外になる点である。対策は「もう一度List」ではなく、LISTEN発行の完了を待ってから購読者登録を有効にする（現状の単一チャンネル方式がプロセス起動時に守っている順序と同じ順序を、動的管理でも維持する）ことに尽きる。
- **チャンネル名のサニタイズが必要になる。** `pg_notify`の第1引数はSQL識別子相当の制約を受けるため、userIDを直接チャンネル名に埋め込む場合は妥当性確認が要る。

## 3. タブ数比例のクエリ増加を解決する案

`Hub`が担う役割を「合図を送るだけ」から「更新後のデータそのものを1回だけ取得して配る」に変える。

```
現状:
  NOTIFY → dispatch → 各タブのtriggerChに合図
                          ↓（タブごとに個別に）
                      JobStore.List ×タブ数分

改善案:
  NOTIFY → dispatch → JobStore.List ×1回
                          ↓
                      結果を各タブのchに配る ×タブ数分（クエリなし）
```

この案は2.の分割案とは完全に独立した対策であり、両者は併用できる。分割案が「プロセス間の無駄な配信」を減らし、この案が「プロセス内の重複クエリ」を減らす、という役割分担になる。

実装するなら、ユーザーごとの参照カウントと最新スナップショットのキャッシュを持つ層を`Hub`とは別に一枚挟む設計が、責務の分離として素直になる。`Hub`自体にPostgreSQLへのクエリ責務まで持たせると、「LISTEN/NOTIFYの配送」という元々の役割から逸脱する。

### Mutation経路からの直接配信という代替案は複数プロセスでは不成立

Mutationリゾルバが更新済みのJob値を持っている以上、それをそのまま同一プロセス内の`Hub`へ渡してNOTIFYを介さず配信する案も検討したが、これは複数プロセスをまたぐ通知を提供できないため、今回の制約（複数プロセス必須）の下では不成立である。プロセスをまたぐ通知には、何らかの形で全プロセスから見える共有の仕組み（PostgreSQL NOTIFY、あるいはRedis等の外部ブローカー）を経由する必要があり、Redis禁止の制約下ではNOTIFYを使い続ける以外の現実的な選択肢がない。

## 4. まとめ

| 課題 | 対策 | 解決するもの | 新たなコスト |
|---|---|---|---|
| プロセス間の無駄な配信 | チャンネルのユーザー単位分割 | 無関係プロセスへの配信 | 動的LISTEN管理、取りこぼしの競合窓 |
| プロセス内のクエリ重複 | dispatch時に1回だけList、結果を全タブへ配布 | タブ数比例のクエリ増加 | Hubまたは別層でのスナップショットキャッシュ管理 |

両方を組み合わせれば、PostgreSQL NOTIFYを使い続けたまま、複数プロセス構成でもタブ数に対する単調増加を解消できる。ただし即時性はNOTIFYの配送保証の限界（取りこぼし時は次の通知まで復元されない）に依存したままであり、この性質自体は変わらない。

表の使用について、CLAUDE.mdの規約上は原則リストを優先するが、対策と効果とコストの対応関係が本質的に表形式のデータであるため、ここでは表を用いた。
